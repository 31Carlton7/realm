# Realm Plan 23 — Scoped downloads from browser panes

> Numbered 23: 22 is the in-flight plan another session is building today (2026-09-02) and is not on
> this branch. Renumber on landing if it collides.
>
> **This plan deliberately reverses a hard block.** `blockBrowserDownloads`
> (`apps/desktop/src/main/browser-pane.ts:139`) cancels every download on the `persist:browser`
> partition, in every permission mode, and its comment states the reason: *"an agent-triggered
> download writes to disk outside every guard Realm has, and the pane is not a download manager for
> the user either."* Both halves of that are still true. What follows is not an argument that the
> block was wrong; it is a proposal to replace one blunt guard with a set of narrow ones, each of
> which can be named and tested. If the narrow guards cannot all be built, the block stays.

> **Built (2026-09-02): W1–W5, all of it.** One deviation in W3 and one refinement in W4, both below.
>
> **W4 as built** is not the "arm, then click" button this plan sketched — that shape requires the
> user to anticipate a download before making it, which is backwards. Instead a blocked download is
> REMEMBERED (`BlockedDownloads`) and the pane shows a bar naming it with a Save button; pressing it
> re-fetches via `webContents.downloadURL` through the same governor, same grant, same allowlist,
> same cap. Same mechanism the plan specified (renderer → IPC → arm), better trigger: the user clicks
> the link naturally, and the consent arrives after they can see what they are consenting to.
>
> Its limit, which is real: a re-fetch is a fresh GET carrying the session's cookies, so a download
> generated by a POST or handed out behind a one-time token will not come back. It fails honestly
> rather than appearing to work.
>
> One deviation in W3: the downloaded
> filename is **clipped and quoted, not `fenceUntrusted`-wrapped**. The fence is a multi-line preamble
> designed for blocks of page text and reads as nonsense around a single token mid-sentence; what
> actually makes the name safe is that it is the name main *wrote*, already reduced by
> `safeAttachmentName` to `[\w.\- ]` and 120 characters, so it cannot carry a newline or a marker of
> its own. The test asserts the property (one bounded line, no breakout) rather than the mechanism.

## Why now

The credential work (browser sign-ins) made the *login* half of "agent, go get my course materials"
near-automatic. It did nothing for the *retrieval* half, and retrieval is where the workflow actually
dies: an agent can read a page's text with `browser_read` and see it with `browser_screenshot`, but a
lecture PDF or slide deck behind a download link is simply unreachable. For the motivating case —
"pull every study guide from my class and build one interactive guide" — the sign-in improvements are
necessary and not close to sufficient.

## The constraint that shapes the whole design

**`will-download` cannot tell a human's click from an agent's.** It fires on the partition, after the
fact, with a `WebContents` and an item. Chromium does not record what dispatched the input, and CDP's
`Input.dispatchMouseEvent` is indistinguishable from a real click by construction — that is the point
of it.

This has a consequence that kills the obvious design. "Let the user download things themselves, keep
blocking the agent" is **not implementable at this layer**: any rule permissive enough to let a human
click through is exactly as permissive for `browser_act`. So:

- Downloads stay **default-deny** at `will-download`, forever. There is no mode, setting, or
  allowlist that makes the handler permissive.
- A download happens only against a **live, one-shot, main-process grant** that was created by an
  already-approved server-side act, and dies when that act's op returns.
- **User-initiated downloads remain blocked at `will-download`.** The human's own consent can only
  arrive out of band: an IPC call from the renderer, which a page cannot reach (its own
  `WebContentsView`, contextIsolation, no preload) and therefore cannot forge. That is W4.

## Architecture

One new bridge op, `download`, orchestrated entirely in Electron main so the grant's lifetime is the
op's lifetime rather than a timer somebody has to reason about.

```
agent → browser_download { browserId, ref }
  server  validate row + space scope + constraints            (agent-tools.ts)
  server  bridge "describe" ref → live origin + link label
  server  broker.gate(card: origin, link text, destination)   (permissions.ts)
  server  bridge "download" { browserId, ref, origin } ──────► main
                                                    main  arm one-shot grant for this wc
                                                    main  click the ref (existing performAct path)
                                                    main  will-download: grant? → confine + allow
                                                                          else → preventDefault
                                                    main  await done/failed, consume grant
  server  ◄──────────────── { ok, name, bytes, relPath } ─────┘
  server  fence the page-authored filename, return to agent
```

The grant is a single field on the pane entry — `{ origin, expiresAt }`, consumed on first use — not
a map, not a queue. A page that fires three downloads on one click gets one through and two
cancelled, which is the correct answer and falls out of the design rather than needing a rule.

## W1 — Destination and contracts

**Where files land.** `<project.rootPath>/downloads/`, where `project` is the space's project
(`ProjectsStore`, `Project.rootPath`). Chosen over a Realm-owned directory for one reason: a project
root is a git repo, so every downloaded file shows up in the diff pane as untracked, and the space's
standing workflow ("ship through the diff pane") already covers reviewing it. A download the user
never sees is the failure mode this is trying to avoid.

A space with **no project has no destination and the tool refuses**, honestly, naming the fix. Do not
invent `<home>/downloads/<spaceId>/` as a fallback — it puts files somewhere no existing surface
looks, which is how you get a silent accumulation nobody audits.

> **Decision for you:** if you would rather downloads never touch a git repo, the alternative is
> `<home>/downloads/<spaceId>/` plus a Documents-pane root so they remain visible. It costs the diff
> pane's review-for-free and needs a sweep policy. My recommendation is the project root.

**Contracts** (`packages/contracts/src/browser-agent.ts`):

- Extend `BrowserRefusal` with `"download_blocked"` (type refused by the allowlist), `"too_large"`,
  `"no_destination"`. Same posture as the existing members: hard blocks, decided in the executor,
  never mode-dependent.
- `BrowserDownloadResult = { ok: true; name: string; bytes: number; relPath: string } | { ok: false;
  error: string; refused?: BrowserRefusal }`.
- `DOWNLOAD_ALLOWED_EXTENSIONS` — an **allowlist**, not a denylist, and this is the single most
  load-bearing choice in the plan. A denylist of executables is a list of the ones you thought of;
  this feature's whole risk is that it turns "an agent reads the web" into "an agent writes files to
  your disk," and only an allowlist bounds that. Start at documents and archives: `pdf docx doc pptx
  ppt xlsx xls csv txt md rtf zip png jpg jpeg gif svg epub`. A file with no extension is refused.
- `DOWNLOAD_MAX_BYTES` — separate from `MAX_ATTACHMENT_BYTES` (20 MB); a lecture deck can exceed it.
  Propose 100 MB.

## W2 — Electron main

`blockBrowserDownloads` becomes `governBrowserDownloads`, same one-time partition registration, same
default of `event.preventDefault()`. What changes is one branch:

1. Look up the browser id for `wc.id` (the existing `browserIdForWebContents` map).
2. No live grant, or grant origin ≠ the item's URL origin, or grant expired → `preventDefault()`,
   note it in the console ring buffer exactly as today.
3. Extension not in the allowlist → `preventDefault()`, refuse as `download_blocked`.
4. Otherwise: `item.setSavePath(join(downloadsDir, uniqueName(safeAttachmentName(item.getFilename()))))`
   and let it run. **The page never influences the directory.** `safeAttachmentName`
   (`attachments.ts:34`) already strips to a basename and a conservative character set — reuse it
   rather than writing a second sanitizer that can disagree with the first.
5. Cap enforcement on `updated`: cancel past `DOWNLOAD_MAX_BYTES` by watching
   `item.getReceivedBytes()`, **not** `getTotalBytes()`, which is 0 for chunked responses and is
   attacker-controlled anyway.
6. On `done`, resolve the op with `{ name, bytes, relPath }`; on interrupt/cancel, resolve as a
   failure. Consume the grant in a `finally` so no path leaves it armed.

**To verify during build, not assume:** whether Chromium applies the `com.apple.quarantine` xattr to
a download whose path came from `setSavePath`. If it does not, main sets it. A downloaded executable
that skips Gatekeeper because Realm wrote it is precisely the outcome the original block prevented —
and the extension allowlist is a mitigation for this, not a substitute.

## W3 — The tool surface

`browser_download { browserId, ref }`, mutating, gated through the existing broker.

- **Card copy:** `Download "<link text>" from <origin> into <project>/downloads`. The link text is
  page-authored, so it is clipped and attributed the way `describeAct` already attributes element
  names — never laundered into Realm's own voice.
- **Mode parity, unlike the credential fill.** `bypassPermissions` skips the card here. A download is
  not a secret leaving the machine, and the hard blocks that matter — path confinement, the extension
  allowlist, the size cap, the one-shot grant — are unconditional and do not consult a mode. Making
  this a second `alwaysPrompt` tool would train prompt-fatigue on the one workflow that legitimately
  needs twenty of them in a row.
- **Batchable — and this is deliberate.** "Every study guide in the class" is twenty downloads; a
  tool that cannot batch makes the motivating workflow twenty cards. `runBatchMutation` must gain a
  `browser_download` branch that repeats *every* validation and hard block and skips only the prompt
  — the same contract the other mutating tools already keep there. The batch card names the count.
- Each download counts against `BrowserAgentConstraints.maxActs`, so a delegated browser-agent child
  cannot spend its budget silently.

## W4 — The user's own downloads

The thing W4 removes is a SILENT failure. Before it, a user clicking a download link in a pane got
nothing: no file, no message, just a link that did not work.

- `BlockedDownloads` (in `downloads.ts`) remembers what was blocked, per pane, capped and expiring.
  The renderer is handed `{ id, name, retryable, ts }` — **never the URL**, and the name already
  through `safeAttachmentName`, so the UI holds neither an address list nor anything page-authored.
- `retryable` is false for anything the extension allowlist would refuse anyway. Those are still
  SHOWN — silence is the bug — but offered no Save button, because a button that cannot work is a lie.
- The pane renders a bar BETWEEN the chrome and the view host, never a floating toast: the native
  view composites over everything in its rectangle, so a toast there would be invisible (W2's
  no-overlay invariant, which W4 has to obey like everything else).
- `browsers.downloadDir` is a new RPC over the shared `spaceDownloadDir` resolver, so the user's
  downloads land exactly where the agent's do by exactly the same rule. Two resolvers would drift,
  and the one that drifted would be writing files somewhere nobody looks.

## W5 — Mutants that must die

Per the house rule, each of these is a one-line change that a test must catch. All eight are covered:
1–6 in `apps/desktop/src/main/downloads.test.ts`, 7–8 in
`apps/server/src/browsers/agent-tools.test.ts`, plus the allowlist's own properties in
`packages/contracts/src/browser-agent.test.ts`.

1. **Path escape.** `item.getFilename()` of `../../.ssh/authorized_keys` (and `..\..\`, and a name
   with a NUL) lands inside `downloads/` under a flattened name, or not at all.
2. **The allowlist inverted or dropped.** `.dmg`, `.pkg`, `.command`, `.sh`, and a no-extension file
   are each refused with `download_blocked`; a `.pdf` is allowed.
3. **Grant outliving its op.** A page-initiated download arriving one tick after `browser_download`
   returns is cancelled. (Test by firing `will-download` twice for one grant.)
4. **Size cap read from the wrong number.** A response reporting `getTotalBytes() === 0` that streams
   past the cap is still cancelled.
5. **Origin drift.** The pane navigates between the card and the click; the item's origin no longer
   matches the granted origin → cancelled. (Same class as the credential fill's origin gate, same
   reason: the approved thing and the executed thing must be the same thing.)
6. **Default-deny regressed.** With no grant at all, `will-download` still calls `preventDefault()` —
   the assertion that the whole plan rests on, and the one most likely to rot.
7. **A page-authored filename reaching a tool result or a card unfenced.**
8. **`runBatchMutation` routing around a hard block** — a batched download that skips the allowlist.

## What this does and does not unlock

With W1–W3 landed, "download every study guide from my class and build one interactive guide" runs
end to end **after** a one-time manual step: you sign in once (credential fill for username and
password, then you clear 2FA yourself — the partition is `persist:browser`, so the cookie persists
and later runs skip it). From there the agent snapshots the course page, batches the downloads into
`downloads/`, and the existing `study-guide` skill takes it from there.

Still not automated, and not in scope:

- **2FA**, for the reasons already documented. Unchanged by this plan.
- **Anything behind a viewer that never serves a file** — an LMS that renders slides in a canvas-based
  reader with no download link has nothing for this to click. `browser_screenshot` is the fallback and
  it is a poor one.
- **Bulk "export all" flows** that produce a server-side ZIP by email.

## Cost

As built: ~200 lines of main-process change (`downloads.ts` plus the `browser-pane.ts` handler and
the host op), a tool plus a batch branch, contract additions, and 40 tests. W4 remains a small hour.

The risk was never volume; it is that this reverses a deliberate hard block, so the review that
matters is on mutants 2, 3 and 6 — the allowlist, the one-shot grant, and default-deny — rather than
on whether it works.

## Still open

- **The macOS quarantine xattr.** Whether Chromium applies `com.apple.quarantine` to a download whose
  path came from `setSavePath` was flagged in this plan as something to verify rather than assume, and
  it has NOT been verified — it needs a real download on a real build, which no unit test can stand in
  for. Until it is, the extension allowlist is the only thing standing between this feature and a
  Gatekeeper bypass, which is a heavier load than it was designed to carry alone. Verify before this
  ships to anyone.
- **POST-generated and one-time-token downloads** cannot be re-fetched by W4's Save button. Fixing
  that would mean holding the response bytes rather than the URL, which is a different and much
  heavier design (bytes on disk before consent) and was not attempted.
